# ADR-005 : Propriétés CSS logiques et i18n par clés plutôt que gabarits par langue

**Statut** : Proposé
**Date** : 2026-07-15
**Contraintes concernées** : C5 (localisation), C7 (maintenance)
**Tension liée** : T5 — voir [plan-architecture.md](../plan-architecture.md#t5)

## Contexte

Le brief exige une interface traduite en français, anglais et arabe, avec adaptation du sens de lecture (RTL),
maintenue par une équipe de 3 personnes. Naïvement, gérer trois langues dont une en RTL peut se traduire par
trois gabarits de page à maintenir en parallèle.

## Options envisagées

| Option | Avantages | Inconvénients |
|---|---|---|
| **A. Un gabarit de page dédié par langue** | Contrôle visuel maximal par langue | Trois fois le travail de maintenance et le risque de régression, hors de portée de C7 ; le RTL de l'arabe demanderait une réécriture complète du gabarit |
| **B. Propriétés CSS logiques + moteur i18n à clés (ICU), traductions externalisées** | Un seul gabarit ; le RTL devient une bascule d'attribut `dir="rtl"`, pas une réécriture ; traductions gérées comme des données, modifiables sans redéploiement | Discipline à maintenir dans la durée (interdiction des propriétés CSS physiques) ; nécessite un outil de lint pour la faire respecter |
| **C. Traduction automatique à la volée** | Coût de développement minimal | Qualité insuffisante pour une interface d'authentification et de service à la personne ; ne résout pas le RTL (mise en page), seulement le texte |

## Décision

Option **B**. Toute la mise en page utilise des propriétés CSS logiques (`margin-inline`,
`text-align: start`, etc.) dès la première maquette. Les textes sont gérés par un moteur i18n à base de clés
(format ICU), les traductions étant traitées comme des données externalisées (fichiers ou table dédiée),
modifiables sans redéploiement.

## Conséquences

**Positives**
- Un bug ou une amélioration d'interface corrigé une seule fois pour les trois langues.
- L'ajout d'une langue future ne nécessite pas de nouveau gabarit.

**Négatives (compromis assumé)**
- Coût de discipline dès la première maquette : toute l'équipe doit connaître et appliquer les propriétés
  logiques, sous peine de voir la dette de duplication réapparaître progressivement.
- Certaines mises en page complexes (tableaux de créneaux horaires) demandent malgré tout une vérification
  RTL spécifique, l'automatisation générale ne couvrant pas tous les cas.

## Révision

Si une langue future introduite ne relève ni du script latin ni d'un RTL simple (par exemple une écriture
verticale), réévaluer l'hypothèse selon laquelle les propriétés CSS logiques suffisent seules.
